What is SQL?

SQL (Structured Query Language) is the standard language for defining, querying and changing data in relational databases — you describe what you want, the database works out how.

Relational database — data stored in tables (relations) of rows (records/tuples) and columns (attributes/fields). Tables are linked by shared key values, not by pointers.

SQL — a declarative language (pronounced “S-Q-L” or “sequel”), standardised by ANSI/ISO since 1986. Every relational database speaks it, each with its own dialect.

Tables, rows and columns

A table has a fixed set of named, typed columns and any number of rows. Every row should be identifiable by a primary key.

SQL
SELECT emp_id, name, salary
FROM employees
WHERE salary > 100000
ORDER BY salary DESC;
Output
emp_id | name  | salary
-------+-------+-------
1      | Asha  | 150000
2      | Ravi  | 120000
5      | Priya | 110000

Read it as English: give me the id, name and salary of employees earning over 1,00,000, highest first. There is no loop, no index handling, no file access — the query optimizer decides how to fetch the rows.

Declarative vs procedural

Declarative (SQL)

You state the result: which rows, which columns, what order. The engine picks indexes, join algorithms and order of work.

Procedural (Python, Java)

You state the steps: open, loop, compare, append, sort. You own the algorithm and its performance.

Why relational databases?

Integrity

Types, keys and constraints reject bad data before it is stored.

Transactions (ACID)

Multi-step changes happen completely or not at all, even across crashes.

Ad-hoc queries

Any question answerable from the data can be asked later — no new code paths needed.

Concurrency

Hundreds of users read and write safely at the same time.

Convention

SQL is case-insensitive for keywords (select = SELECT). Convention: keywords in UPPER CASE, table and column names in snake_case. String literals use single quotes: 'Mumbai'.

What is the difference between SQL and MySQL?

SQL is the language (an ISO standard). MySQL is one database product (an RDBMS) that implements SQL with its own extensions — like PostgreSQL, SQL Server, Oracle and SQLite.

What does “declarative” mean for SQL?

You describe the result set you want, not the algorithm. The optimizer chooses the execution plan (index vs full scan, join order, hash vs nested-loop join), so the same query can get faster when indexes are added without changing a line of SQL.

Which SQL database should you choose for a new project?

Default to PostgreSQL for a general server-side app (standards, JSONB, extensions). MySQL is equally fine and widely hosted. SQLite for embedded/mobile/local tools and tests. SQL Server or Oracle usually when the organisation already runs them.

Is SQLite a “real” database?

Yes — it is fully transactional (ACID) and is the most deployed database in the world (every phone and browser). What it lacks is a server: no network access, no user accounts/GRANT, and one writer at a time. It is ideal for local data, not for many concurrent writers.

SQL commands are grouped by what they act on — the structure, the data, permissions, or transactions. A classic first interview question.

One of each
SQL
-- DDL: define structure
CREATE TABLE notes (id INTEGER PRIMARY KEY, body TEXT NOT NULL);

-- TCL + DML: change data inside a transaction
BEGIN;
INSERT INTO notes (body) VALUES ('learn SQL'), ('practice joins');
UPDATE notes SET body = 'practice window functions' WHERE id = 2;
COMMIT;

-- DQL: read it back
SELECT id, body FROM notes ORDER BY id;
Output
id | body
---+--------------------------
1  | learn SQL
2  | practice window functions
PostgreSQL / MySQL / SQL Server
-- DCL: permissions (server databases only; SQLite has no users)
GRANT SELECT, INSERT ON notes TO analyst;
REVOKE INSERT ON notes FROM analyst;
Why the grouping matters

Auto-commit of DDL

In MySQL and Oracle every DDL statement implicitly commits the open transaction and cannot be rolled back. PostgreSQL and SQLite allow DDL inside a transaction.

Permissions

DBAs grant DDL rights to few people (schema owners), DML to applications, and read-only DQL to analysts.

Is TRUNCATE DDL or DML?

DDL in most engines. It removes all rows by deallocating data pages instead of deleting row by row, does not fire DELETE triggers, resets identity counters, and (in MySQL/Oracle) auto-commits. DELETE is DML: row by row, logged, can have a WHERE, can be rolled back.

Is SELECT part of DML?

Formally the SQL standard puts SELECT under data manipulation; many courses split it out as DQL. Either answer is accepted if you explain that SELECT only reads data.

CHAR vs VARCHAR

CHAR(10)

Always 10 characters — 'abc' is stored as 'abc' + 7 spaces. Slightly faster for truly fixed-length values (country codes, hashes).

VARCHAR(10)

Up to 10 characters, stores only the actual length plus a small length prefix. The default choice for text.

Money: DECIMAL, never FLOAT

SQLite

SQLite has no separate DATE/BOOLEAN storage: dates are stored as ISO-8601 text ('2024-03-15') or numbers, booleans as 0/1. That is why the sample database uses TEXT for dates — ISO strings sort and compare correctly.

Choosing types
Do

Pick the smallest correct type (INT over BIGINT if it can never exceed 2 billion), DECIMAL for money, DATE/TIMESTAMP for time, and the same type on both sides of a foreign key.

Avoid

Store dates or numbers as free text in a real engine, use FLOAT for money, or give every text column VARCHAR(255) without thinking about the real limit.

What is the difference between DECIMAL and FLOAT?

DECIMAL(p,s) is exact base-10 arithmetic with fixed precision — right for money. FLOAT/DOUBLE are approximate binary floating point: faster and with a huge range, but 0.1 + 0.2 is not exactly 0.3, so sums of prices drift.

What is the difference between VARCHAR and TEXT?

In PostgreSQL they are the same storage; VARCHAR(n) just adds a length check. In MySQL, TEXT columns are stored off-page and have indexing restrictions (need a prefix length) and no default value, so VARCHAR(n) is preferred for short strings.

Watch out

DROP and TRUNCATE cannot be undone in MySQL and Oracle (they auto-commit). Take a backup, and never run DDL on production without a reviewed migration.

DELETE vs TRUNCATE vs DROP?

DELETE removes chosen rows one by one (DML, logged, triggers fire, rollback-able). TRUNCATE empties the whole table quickly by deallocating storage (DDL, no WHERE, no triggers, resets identity). DROP removes the table itself — structure, data, indexes, constraints.

Can TRUNCATE be used on a table referenced by a foreign key?

Generally no — SQL Server and MySQL refuse to truncate a table referenced by a foreign key; PostgreSQL requires TRUNCATE … CASCADE to also empty the referencing tables. DELETE works if no child rows reference the deleted rows.

What is the difference between PRIMARY KEY and UNIQUE?

Both enforce uniqueness and create an index. A table has one primary key and it can never be NULL; it is the row's identity and the target of foreign keys. A table can have many UNIQUE constraints and they allow NULLs (multiple, in most engines).

Can a foreign key column be NULL?

Yes, unless it is also NOT NULL. A NULL foreign key means “no related row” (e.g. Dev has no department). The constraint is only checked for non-null values.

Why enforce constraints in the database if the application validates input?

Several applications, scripts, admins and migrations write to the same database; bugs and race conditions happen (two requests inserting the same email at once). Only the database sees every write and can guarantee integrity atomically.

How do you delete rows from one table based on another table?

Use a subquery — DELETE FROM a WHERE id IN (SELECT a_id FROM b WHERE …) or WHERE EXISTS (SELECT 1 FROM b WHERE b.a_id = a.id …). MySQL and SQL Server also allow a join form: DELETE a FROM a JOIN b ON … WHERE …; PostgreSQL has DELETE FROM a USING b WHERE ….

What happens if you run UPDATE without WHERE?

Every row in the table is updated. If you are inside an explicit transaction you can ROLLBACK; in autocommit mode the change is permanent and you need a backup or point-in-time recovery. MySQL's --safe-updates mode refuses UPDATE/DELETE without a key-based WHERE or LIMIT.

UPSERT: Insert or Update

An upsert inserts a row, or updates it if a row with the same key already exists — atomically, in one statement, without a race between “check” and “write”.

INSERT … ON CONFLICT (PostgreSQL, SQLite)
SQL
CREATE TABLE inventory (
    sku        TEXT PRIMARY KEY,
    qty        INTEGER NOT NULL,
    updated_on TEXT NOT NULL
);
INSERT INTO inventory VALUES ('PEN', 100, '2024-03-01'), ('DESK', 5, '2024-03-01');

INSERT INTO inventory (sku, qty, updated_on) VALUES
    ('PEN',   50, '2024-03-10'),      -- exists  → add to stock
    ('CHAIR', 12, '2024-03-10')       -- new     → insert
ON CONFLICT (sku) DO UPDATE
    SET qty        = inventory.qty + excluded.qty,
        updated_on = excluded.updated_on;

SELECT * FROM inventory ORDER BY sku;
Output
sku   | qty | updated_on
------+-----+-----------
CHAIR | 12  | 2024-03-10
DESK  | 5   | 2024-03-01
PEN   | 150 | 2024-03-10

excluded is the row that would have been inserted; inventory.qty is the existing row. ON CONFLICT (sku) DO NOTHING simply skips duplicates.

Other dialects
MySQL
INSERT INTO inventory (sku, qty, updated_on) VALUES ('PEN', 50, '2024-03-10')
ON DUPLICATE KEY UPDATE
    qty = qty + VALUES(qty),          -- MySQL 8.0.20+: prefer an alias, e.g. AS new … new.qty
    updated_on = VALUES(updated_on);
SQL Server / Oracle / PostgreSQL 15+ (MERGE)
MERGE INTO inventory AS t
USING (VALUES ('PEN', 50, '2024-03-10')) AS s (sku, qty, updated_on)
    ON t.sku = s.sku
WHEN MATCHED THEN
    UPDATE SET qty = t.qty + s.qty, updated_on = s.updated_on
WHEN NOT MATCHED THEN
    INSERT (sku, qty, updated_on) VALUES (s.sku, s.qty, s.updated_on);
The REPLACE trap

SQLite's INSERT OR REPLACE (and MySQL's REPLACE) deletes the old row and inserts a new one — columns you did not supply fall back to defaults.

SQL
CREATE TABLE users (id INTEGER PRIMARY KEY, name TEXT, plan TEXT DEFAULT 'free');
INSERT INTO users VALUES (1, 'Asha', 'premium');

INSERT OR REPLACE INTO users (id, name) VALUES (1, 'Asha R');   -- plan is lost!
SELECT * FROM users;
Output
id | name   | plan
---+--------+-----
1  | Asha R | free
Watch out

REPLACE also fires delete triggers and can cascade-delete child rows. Prefer ON CONFLICT … DO UPDATE / ON DUPLICATE KEY UPDATE, which update in place.

Race condition

“SELECT then INSERT or UPDATE” in application code is a race: two requests can both see “not found” and both insert. Upsert statements (or a unique constraint plus retry) make it atomic.

How do you implement an upsert?

Put a UNIQUE/PRIMARY KEY on the natural key, then use the engine's atomic form: INSERT … ON CONFLICT (key) DO UPDATE SET … = excluded.… (PostgreSQL/SQLite), INSERT … ON DUPLICATE KEY UPDATE (MySQL), or MERGE (SQL Server/Oracle/PostgreSQL 15+). The conflict target must be backed by a unique index.

What is the difference between != and <>?

None in practice — <> is the ISO standard “not equal”, != is accepted by every major engine. Both yield unknown (not true) when either side is NULL.

Yes, both ends: x BETWEEN a AND b means x >= a AND x <= b. If a > b it matches nothing (SQL Server/MySQL) — BETWEEN SYMMETRIC in PostgreSQL swaps them for you.

LIMIT, OFFSET & Pagination

LIMIT caps the number of rows returned; OFFSET skips rows first. Together they page through results — but deep offsets get slow.

Top-N
SQL
SELECT name, salary FROM employees
ORDER BY salary DESC, emp_id
LIMIT 3;
Output
name  | salary
------+-------
Asha  | 150000
Ravi  | 120000
Priya | 110000
Watch out

LIMIT without ORDER BY returns an arbitrary 3 rows. And when the sort key has ties (Meera and Karan both 95000), add a unique tie-breaker (emp_id) so pages are stable.

Offset pagination

OFFSET 100000 still reads and throws away 100 000 rows, and rows inserted between requests shift pages (duplicates / gaps). Keyset pagination remembers the last key seen and seeks past it using the index.

SQL
-- the client got page 1 ending at emp_id = 3; next page:
SELECT emp_id, name FROM employees
WHERE emp_id > 3
ORDER BY emp_id

5      | Priya
6      | Arjun

ORDER BY salary DESC, emp_id DESC
LIMIT 3;

9      | Sara   | 85000
8      | Vikram | 80000

Offset pagination

Simple, allows jumping to page N. Cost grows with the offset; unstable when data changes.

Keyset pagination

Constant speed on any page, stable under inserts. No random page jumps — ideal for infinite scroll and APIs (?after=…).

Why is OFFSET pagination slow for large page numbers?

The database must produce and discard every row before the offset — OFFSET 1000000 reads a million rows to return 20. Keyset pagination (WHERE key > :last ORDER BY key LIMIT 20) jumps straight to the starting point through the index.

NULL means unknown / missing. It is not zero, not an empty string, and not equal to anything — not even another NULL.

What is the difference between NULL, 0 and an empty string?

0 and '' are known values that compare and sort normally. NULL is the absence of a value: comparisons with it yield UNKNOWN, it is skipped by aggregates and needs IS NULL. (Oracle is odd: it treats '' as NULL.)

Why does WHERE col <> 'x' not return rows where col is NULL?

NULL <> 'x' is UNKNOWN, and WHERE keeps only TRUE. Write WHERE col <> 'x' OR col IS NULL, or WHERE col IS DISTINCT FROM 'x'.

CASE is SQL's if/else. It is an expression — it returns a value and can be used anywhere a value can: SELECT, WHERE, ORDER BY, GROUP BY, inside aggregates.

SQL
SELECT COUNT(*)                                           AS orders,
       SUM(CASE WHEN status = 'delivered' THEN 1 ELSE 0 END) AS delivered,

Can you use CASE in a WHERE clause?

Yes — it is just an expression: WHERE CASE WHEN :role = 'admin' THEN 1 WHEN owner_id = :me THEN 1 ELSE 0 END = 1. But plain AND/OR logic is usually clearer and friendlier to indexes.

Watch out

What is the difference between COUNT(*), COUNT(1) and COUNT(column)?

COUNT(*) and COUNT(1) both count rows and perform the same in modern engines. COUNT(column) counts rows where that column is not NULL. COUNT(DISTINCT column) counts distinct non-null values.

Does AVG include NULL values?

No. AVG(x) = SUM(x) / COUNT(x) over non-null values only. To treat missing as zero, use AVG(COALESCE(x, 0)).

Can you GROUP BY a column that is not in the SELECT list?

What does GROUP BY do with NULL values?

It treats all NULLs in the grouping column as one group (even though NULL = NULL is not true). The group shows up with NULL as its key.

What is the difference between LEFT JOIN and INNER JOIN?

INNER JOIN returns only rows with a match on both sides. LEFT JOIN returns every row of the left table, with the right table's columns NULL where there is no match. The row count of a left join is always ≥ the left table's count (more if one left row matches several right rows).

How do you emulate FULL OUTER JOIN in MySQL?

LEFT JOIN the two tables, then UNION ALL the rows of the right table that have no match (RIGHT JOIN … WHERE left.key IS NULL or NOT EXISTS). Plain UNION of a LEFT and a RIGHT join also works but de-duplicates, which can drop genuine duplicate rows.

What is the difference between UNION and UNION ALL?

UNION removes duplicate rows from the combined result (extra sort/hash work); UNION ALL keeps every row and is faster. Use UNION ALL when the inputs can't overlap or duplicates are wanted.

What is the difference between UNION and JOIN?

UNION stacks the rows of two compatible queries (same columns) — the result has more rows. JOIN matches rows of two tables on a condition — the result has more columns.

What is a CTE and why use it?

A Common Table Expression is a named, temporary result defined with WITH and visible only to the statement that follows. It improves readability (step-by-step logic), lets you reference the same intermediate result several times, and is required for recursive queries.

Is a CTE faster than a subquery?

Usually neither — most optimizers treat a non-recursive CTE like an inline subquery. It can be faster if it is materialised once and referenced many times, or slower if materialisation blocks predicate push-down. Choose it for clarity and check the plan when performance matters.

Window Functions: The Basics

A window function computes a value across a set of related rows — without collapsing them like GROUP BY does. Each row keeps its identity and gains an aggregate, a rank or a neighbour's value.

OVER clause — f(…) OVER (PARTITION BY … ORDER BY … frame) — PARTITION BY splits rows into independent groups, ORDER BY orders rows inside each partition, the frame picks which rows around the current one are included.

GROUP BY vs window
SQL
-- GROUP BY: one row per department
SELECT dept_id, AVG(salary) AS dept_avg
FROM employees WHERE dept_id IN (2, 3)
GROUP BY dept_id
ORDER BY dept_id;

-- window: every employee kept, department average attached
SELECT name, dept_id, salary,
       AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg,
       salary - AVG(salary) OVER (PARTITION BY dept_id) AS diff
FROM employees WHERE dept_id IN (2, 3)
ORDER BY dept_id, emp_id;

What is the difference between GROUP BY and a window function?

GROUP BY collapses each group into one output row, so you lose row detail. A window function computes over a group (the partition) but returns a value on every row — so you can show each employee next to their department average, rank or running total.

What is PARTITION BY?

The window equivalent of GROUP BY: it splits rows into independent partitions, and the window function restarts for each one. Without it, the whole result set is a single partition.

How do you calculate a running total in SQL?

SUM(amount) OVER (ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW), adding PARTITION BY to restart per group. Without window functions: a correlated subquery (SELECT SUM(amount) FROM t t2 WHERE t2.day <= t.day) — O(n²).

What is the difference between ROWS and RANGE?

ROWS defines the frame by physical row count (2 PRECEDING = the two rows before). RANGE defines it by value of the ORDER BY key, so all rows with the same key (peers) are included together — which is why the default frame gives tied rows the same running total.

What is the difference between a view and a table?

A table stores rows. A (regular) view stores only a query; reading it runs the query against the base tables, so it is always up to date and uses no extra storage. Views give abstraction and security; they don't make queries faster by themselves.

Can you insert into a view?

If the view is updatable — typically a single base table, no aggregates/DISTINCT/GROUP BY/set operators, and it includes all NOT NULL columns without defaults. Otherwise, use INSTEAD OF triggers (SQL Server, Oracle, PostgreSQL, SQLite).

Indexes

An index is a separate, sorted structure that lets the database find rows without scanning the whole table — like the index at the back of a book. It speeds reads and slows writes.

B-tree: the default index

A B-tree (B+tree) keeps keys sorted in a shallow, balanced tree: a lookup touches ~3–4 pages even for millions of rows (O(log n)), and because keys are sorted it also serves ranges, prefixes and ORDER BY.

Clustered vs non-clustered

Clustered index

The table rows themselves are stored in index order — one per table. InnoDB and SQL Server cluster on the primary key; SQLite tables are clustered on rowid.

Non-clustered (secondary)

A separate structure of key + pointer (row id or primary key) back to the table. Many per table; a lookup may need an extra hop to fetch the row.

The cost side
  • Every INSERT, DELETE and indexed-column UPDATE must update every index — write-heavy tables should have few.
  • Indexes take disk and memory (buffer cache).
  • Low-selectivity columns (status with 4 values, booleans) rarely benefit alone — the planner prefers a scan when a large fraction of rows match.
  • Unused and duplicate indexes ((a) next to (a, b)) are pure cost; drop them.
How does an index speed up a query?

It keeps column values sorted in a B-tree with pointers to rows, so the engine can binary-search to the matching keys in O(log n) page reads instead of scanning all rows, and can return rows already sorted for ORDER BY. The price is extra storage and slower writes.

Why might a query not use an index?

The predicate doesn't match the index (function on the column, leading wildcard, implicit type conversion, not the leftmost column of a composite index), OR across different columns, low selectivity so a scan is cheaper, stale statistics, or a tiny table.

Clustered vs non-clustered index?

A clustered index defines the physical order of the table's rows (only one per table, usually the primary key). A non-clustered index is a separate structure with keys and row locators; a table can have many.

Watch out

Triggers are invisible side effects: a simple UPDATE can fan out into cascades of hidden writes, slow bulk loads and surprise developers. Keep them small, document them, and prefer constraints for pure integrity rules.

What are triggers used for, and what are their drawbacks?

Audit trails, keeping denormalised/derived columns in sync, enforcing complex rules constraints can't express, and making views writable. Drawbacks: hidden logic, harder debugging, performance cost on every write (especially row-level triggers on bulk operations), and possible trigger chains.

BEFORE vs AFTER trigger?

BEFORE runs before the row is written — use it to validate or modify NEW values (or reject the change). AFTER runs once the change is applied — use it for side effects like audit rows or updating other tables, when the final values are known.

Autocommit

Outside an explicit BEGIN, most engines run in autocommit mode: every statement is its own transaction. Oracle is the exception — a transaction starts implicitly and you must COMMIT. Python's DB-API and many drivers open transactions for you and require conn.commit().

Do

Keep transactions short: do the reads and computation first, then BEGIN → writes → COMMIT. Long transactions hold locks, block other users and bloat MVCC history.

Explain ACID with a bank transfer.

Atomicity: debit and credit both apply or neither does. Consistency: balances never go negative and total money is preserved (constraints). Isolation: a concurrent report never sees money “in flight” (debited but not yet credited). Durability: once the user sees “transfer complete”, a crash can't undo it.

What is the difference between COMMIT and ROLLBACK?

COMMIT makes all changes of the transaction permanent and visible to others. ROLLBACK discards them, restoring the state at BEGIN (or at a SAVEPOINT with ROLLBACK TO).

                     "INSERT INTO accounts VALUES (1, 1000);")

a.execute("UPDATE accounts SET balance = balance - 200 WHERE id = 1")
print("A sees its change:", read(a))       # A sees its change: 800
print("B, A uncommitted:", read(b))        # B, A uncommitted: 1000   ← no dirty read
a.execute("COMMIT")

b.execute("COMMIT")
print("B, new transaction:", read(b))      # B, new transaction: 800
Key point

Under READ COMMITTED (PostgreSQL's default), B's third read would already return 800 — each statement sees the latest committed data. That's the non-repeatable read the level allows.

Preventing lost updates

Atomic update

UPDATE accounts SET balance = balance - 100 WHERE id = 1 — read-modify-write happens inside one statement. Best when possible.

Pessimistic lock

SELECT … FOR UPDATE locks the row until commit, so the second transaction waits.

Optimistic check

UPDATE … SET balance = :new, version = version + 1 WHERE id = 1 AND version = :read_version — 0 rows updated means someone else won; retry.

Serializable

Let the database detect the conflict and abort one transaction; the app retries.

What isolation level would you use?

Usually the engine default (Read Committed in PostgreSQL/SQL Server/Oracle, Repeatable Read in MySQL) combined with atomic updates or SELECT … FOR UPDATE for read-modify-write. Use SERIALIZABLE for complex invariants spanning several rows (write skew) and be ready to retry on serialization failures.

What is a phantom read?

Re-running the same range query in one transaction returns a different set of rows because another transaction committed an insert or delete in that range. Non-repeatable reads are about changed values of existing rows; phantoms are about rows appearing or disappearing.

Locking, MVCC & Deadlocks

Databases coordinate concurrent transactions with locks and, in most modern engines, MVCC (multi-version concurrency control), so readers and writers rarely block each other.

Lock types

Granularity: row locks (InnoDB, PostgreSQL, SQL Server, Oracle) allow high concurrency; table/page locks are cheaper but block more; SQLite locks the whole database for writing.

MVCC

Instead of overwriting a row in place, an update creates a new version. Each transaction reads the versions that were committed as of its snapshot. Result: readers don't block writers and writers don't block readers; only writer-vs-writer on the same row waits.

  • PostgreSQL keeps old versions in the table (cleaned up by VACUUM).
  • MySQL InnoDB and Oracle rebuild old versions from undo logs.
  • SQL Server uses locking by default; READ_COMMITTED_SNAPSHOT switches reads to row versions.

Real apps set a timeout (busy timeout) so the second writer waits instead of failing immediately.

What is a deadlock and how do databases handle it?

Two (or more) transactions each hold a lock the other needs, so all wait forever. The engine's deadlock detector finds the cycle and rolls back one victim, returning an error (MySQL 1213, SQL Server 1205, PostgreSQL 40P01). Prevent with consistent lock ordering and short transactions; handle by retrying.

Optimistic vs pessimistic locking?

Pessimistic: lock the data before changing it (SELECT … FOR UPDATE), so conflicts wait — good for high contention. Optimistic: don't lock; detect a conflict at write time with a version/timestamp column (WHERE version = :v) and retry — good when conflicts are rare, e.g. web forms.

SQL Injection & Parameterized Queries

SQL injection happens when user input is pasted into SQL text, letting an attacker change the query itself. It is still one of the most common and damaging web vulnerabilities — and it is completely preventable.

The vulnerable pattern

    CREATE TABLE users (id INTEGER PRIMARY KEY, username TEXT, password_hash TEXT, is_admin INTEGER);

    query = f"SELECT id, username FROM users WHERE username = '{name}'"   # ✗ string building

The input x' OR '1'='1 closes the string and adds a condition that is always true, so the query becomes:

SQL
SELECT id, username FROM users WHERE username = 'x' OR '1'='1'

With a login form that is an authentication bypass; with UNION SELECT an attacker can read other tables; with stacked queries ('; DROP TABLE users; --) in engines/drivers that allow them, destroy data.

The fix: bind parameters
Python — parameterized
import sqlite3
db = sqlite3.connect(":memory:")
db.executescript("""
    CREATE TABLE users (id INTEGER PRIMARY KEY, username TEXT);
    INSERT INTO users VALUES (1, 'asha'), (2, 'ravi');
""")

def find_user(name):
    return db.execute("SELECT id, username FROM users WHERE username = ?", (name,)).fetchall()

print(find_user("ravi"))             # [(2, 'ravi')]
print(find_user("x' OR '1'='1"))     # []   ← treated as a plain (odd) username

With a placeholder, the SQL text and the data travel separately; the database parses the query first and the value can never become code.

What parameters can't do

Placeholders stand for values only — not table names, column names, ASC/DESC or keywords. For those, map the user's choice through an allow-list:

Python — allow-list
SORTABLE = {"name": "username", "newest": "id DESC"}

def order_clause(user_choice):
    return "ORDER BY " + SORTABLE.get(user_choice, "id")    # never interpolate the raw input

print(order_clause("newest"))                    # ORDER BY id DESC
print(order_clause("id; DROP TABLE users"))      # ORDER BY id
Defence in depth
  • Parameterized queries or an ORM everywhere — including admin tools and scripts.
  • Least privilege: the app's DB user can't DROP, can't read tables it doesn't need.
  • Validate input types and lengths; escape output (injection's cousin is XSS).
  • Don't show raw database errors to users; log them.
  • Watch ORM escape hatches: raw SQL helpers, .extra(), string-built WHERE fragments.
Watch out

Escaping quotes by hand (name.replace("'", "''")) is fragile — character sets, numeric contexts and second-order injection (stored input reused later) break it. Use bind parameters.

What is SQL injection and how do you prevent it?

An attack where untrusted input is concatenated into a SQL string and changes the query's structure (' OR '1'='1, UNION SELECT …, ; DROP …). Prevent it with parameterized queries/prepared statements (or an ORM using them), allow-lists for identifiers, least-privilege database accounts, and input validation.

Do stored procedures prevent SQL injection?

Only if they use parameters properly. A procedure that builds dynamic SQL by concatenating its arguments (EXEC('SELECT … ' + @name)) is just as injectable; use sp_executesql with parameters (SQL Server) or EXECUTE … USING (PostgreSQL).

What is the difference between a primary key and a candidate key?

A candidate key is any minimal set of columns that uniquely identifies rows; a table can have several. The primary key is the one candidate key you choose as the table's official identifier (not null, referenced by foreign keys). The others become alternate keys with UNIQUE constraints.

Can a table have no primary key?

Technically yes in most engines (a heap), but it is almost always a mistake: duplicates can't be prevented or targeted, replication and ORMs struggle, and InnoDB creates a hidden one anyway. Every table should have a primary key.

How do you implement a many-to-many relationship?

With a junction (bridge/associative) table holding a foreign key to each side, whose primary key is usually the pair of FKs (PRIMARY KEY (student_id, course_id)). Attributes of the relationship itself (grade, quantity, enrolled date) live in the junction table.

Normalization (1NF → BCNF)

Normalization organises columns into tables so that each fact is stored once. It removes update, insert and delete anomalies caused by redundancy.

Functional dependency (A → B) — the value of A determines the value of B: emp_id → name, customer_name → customer_city. Normal forms are rules about which dependencies may exist inside one table.

1NF — atomic values, no repeating groups

Every cell holds one value; no lists, no phone1/phone2/phone3 columns; each row is unique (has a key).

    SELECT order_id, order_date, customer_name, customer_city, '', products || ','
    FROM order_sheet
    UNION ALL
    SELECT order_id, order_date, customer_name, customer_city,
           trim(substr(rest, 1, instr(rest, ',') - 1)),
           substr(rest, instr(rest, ',') + 1)
    FROM split WHERE rest <> ''
)
SELECT order_id, order_date, customer_name, customer_city, product
FROM split WHERE product <> ''
ORDER BY order_id, product;

2NF — no partial dependencies

Applies when the key is composite. Every non-key column must depend on the whole key. Here the key is (order_id, product), but order_date, customer_name, customer_city depend on order_id alone → move them to an orders table. The line table keeps only (order_id, product, quantity…).

3NF — no transitive dependencies

Non-key columns must depend on the key, the whole key, and nothing but the key. In orders(order_id, order_date, customer_name, customer_city), order_id → customer_name → customer_city: city depends on the customer, not the order → move customers to their own table and keep customer_id in orders.

A stricter 3NF. Classic case: teaching(student, course, instructor) where each instructor teaches exactly one course (instructor → course) and a student takes a course from one instructor. Key point

Most OLTP schemas aim for 3NF/BCNF. Going further is rarely needed; going less far should be a deliberate choice (denormalization).

What is normalization and why is it needed?

The process of structuring tables so each fact is stored once, using normal forms (1NF, 2NF, 3NF, BCNF) based on functional dependencies. It prevents update/insert/delete anomalies, saves space and keeps data consistent; the cost is more tables and joins.

What is the difference between 3NF and BCNF?

3NF allows a dependency X → Y where Y is part of a candidate key (a prime attribute) even if X isn't a key. BCNF forbids it: the left side of every non-trivial dependency must be a super key. They differ only when a table has overlapping composite candidate keys.

Star schema

A central fact table of measurable events (sales_fact: quantity, amount) with foreign keys to dimension tables describing them (dim_date, dim_customer, dim_product). Dimensions are wide and denormalised, so queries need one join per dimension.

FROM orders o JOIN order_items oi ON oi.order_id = o.order_id
WHERE o.status <> 'cancelled';

SELECT p.category, c.city, SUM(f.amount) AS revenue
FROM sales_fact f
JOIN products  p ON p.product_id  = f.product_id
JOIN customers c ON c.customer_id = f.customer_id
GROUP BY p.category, c.city
ORDER BY revenue DESC;

Do

Normalise first; denormalise a specific hot path after measuring, with a clear owner of the sync logic (trigger, job, or materialised view).

Avoid

Denormalise “for speed” up front — you pay forever in inconsistent data and complex writes.

When would you denormalize?

When a read path is hot and joins/aggregations are measurably too slow even with good indexes, for reporting/analytics (star schemas), or to cache expensive aggregates (counters). Accept the cost: extra storage, slower writes and code/triggers to keep copies consistent.

What is a star schema?

A data-warehouse design with one central fact table (numeric measures + foreign keys) surrounded by denormalised dimension tables (date, customer, product, store). Snowflake schema = the dimensions are further normalised into sub-dimensions.

Interview Prep

Nth Highest Salary

The most-asked SQL interview question. Know three solutions, and be precise about ties and what to return when there is no Nth value.

Salaries (distinct, highest first): 150000, 120000, 110000, 95000 (Meera and Karan), 85000, 80000, … — so the 4th highest distinct salary is 95000.

1. DENSE_RANK (best general answer)
SQL
WITH ranked AS (
    SELECT name, salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees
)
SELECT name, salary FROM ranked WHERE rnk = 4 ORDER BY name;
Output
name  | salary
------+-------
Karan | 95000
Meera | 95000

Returns every employee with that salary. RANK would skip numbers after ties, and ROW_NUMBER would arbitrarily return only one of Meera/Karan and shift everyone below.

2. LIMIT / OFFSET on distinct salaries
SQL
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 3;          -- N - 1

-- return NULL (not zero rows) when N is too large: wrap it in a scalar subquery
SELECT (SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 99) AS nth_salary;
Output
salary
------
95000

nth_salary
----------
NULL
3. Correlated subquery (no window functions)
SQL
-- the salary that has exactly N-1 distinct salaries above it
SELECT DISTINCT e.salary
FROM employees e
WHERE 3 = (SELECT COUNT(DISTINCT i.salary) FROM employees i WHERE i.salary > e.salary);
Output
salary
------

How do you delete duplicate rows but keep one?

Number the rows within each duplicate group with ROW_NUMBER() OVER (PARTITION BY <dup columns> ORDER BY id) and delete those with rn > 1; or delete where id NOT IN (SELECT MIN(id) … GROUP BY <dup columns>). If the table has no unique id at all, copy distinct rows to a new table (or use the engine's physical row id: rowid in SQLite, ctid in PostgreSQL).

The islands trick

Within one user, subtract the row number (in days) from the date. Consecutive dates produce the same anchor value; a gap changes it. Group by that anchor and each group is one streak (“island”).

SQL
SELECT user_id, login_date,
       ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) AS rn,
       date(login_date, '-' || ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY login_date) || ' days') AS grp
FROM logins
WHERE user_id = 1
ORDER BY login_date;
Output
user_id | login_date | rn | grp
--------+------------+----+-----------
1       | 2024-03-01 | 1  | 2024-02-29
1       | 2024-03-02 | 2  | 2024-02-29
1       | 2024-03-03 | 3  | 2024-02-29
1       | 2024-03-05 | 4  | 2024-03-01
1       | 2024-03-06 | 5  | 2024-03-01
SQL

    SELECT user_id, login_date,

SELECT user_id, MIN(login_date) AS streak_start, MAX(login_date) AS streak_end, COUNT(*) AS days

       MAX(CASE WHEN subject = 'Math'    THEN score END) AS math,

There is no universal MEDIAN() in SQL. Interviewers ask you to build it from window functions — and to compute running totals and row-to-row differences.

           ROW_NUMBER() OVER (ORDER BY salary) AS rn,

SQL Interview Q&A

Rapid-fire theory questions with crisp answers. Each links to the topic where it is explained with runnable examples.

Fundamentals
What is the difference between DELETE, TRUNCATE and DROP?

DELETE removes selected rows (DML, WHERE, triggers fire, rollback-able). TRUNCATE removes all rows fast by deallocating pages (DDL, no WHERE, resets identity). DROP removes the table itself.

What is the difference between WHERE and HAVING?

WHERE filters rows before grouping and can't use aggregates; HAVING filters groups after GROUP BY and can.

What is the logical order of execution of a SELECT?

FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT.

What is NULL? How do you test for it?

The marker for a missing/unknown value. Comparisons with it are UNKNOWN, so use IS NULL / IS NOT NULL; replace it with COALESCE. Aggregates ignore it; COUNT(*) doesn't.

UNION vs UNION ALL?

Both stack results; UNION removes duplicates (extra sort/hash), UNION ALL keeps them and is faster.

What are the types of joins?

INNER (matches only), LEFT/RIGHT OUTER (all rows of one side), FULL OUTER (all rows of both), CROSS (Cartesian product), plus self joins, non-equi joins, and semi/anti joins via EXISTS/NOT EXISTS.

CHAR vs VARCHAR?

CHAR(n) is fixed length and space-padded; VARCHAR(n) stores only the actual characters plus a length. Use CHAR only for truly fixed-length codes.

Design
Primary key vs unique key?

One primary key per table, never NULL, the row identity and FK target. Many unique keys allowed, NULLs permitted.

What is a foreign key?

A column (set) whose values must exist in the referenced key of another table, enforcing referential integrity, with ON DELETE/ON UPDATE actions (RESTRICT, CASCADE, SET NULL).

What is normalization? Name the normal forms.

Organising data so each fact is stored once: 1NF (atomic values), 2NF (no partial dependency on a composite key), 3NF (no transitive dependency), BCNF (every determinant is a candidate key). Prevents update/insert/delete anomalies.

When would you denormalize?

For measured read-performance needs or analytics (star schemas), accepting redundancy and sync logic.

Advanced querying
What is a CTE? A recursive CTE?

A named subquery defined with WITH for one statement. A recursive CTE references itself (anchor UNION ALL recursive member) to walk hierarchies or generate series.

What are window functions?

Functions computed over a set of rows related to the current row via OVER (PARTITION BY … ORDER BY … frame), without collapsing rows: ranks, running totals, LAG/LEAD.

RANK vs DENSE_RANK vs ROW_NUMBER?

ROW_NUMBER: 1,2,3,4 always unique. RANK: ties share, then a gap (1,2,2,4). DENSE_RANK: ties share, no gap (1,2,2,3).

Correlated vs non-correlated subquery?

A correlated subquery references the outer query and is evaluated per outer row; a non-correlated one runs once independently.

EXISTS vs IN vs JOIN?

EXISTS/IN test membership without duplicating rows (semi join); a JOIN returns combined rows and can multiply them. Prefer NOT EXISTS over NOT IN because of NULLs.

Performance & internals
What is an index? What are its downsides?

A sorted auxiliary structure (usually a B+tree) for fast lookups, ranges and sorts. It costs storage and slows INSERT/UPDATE/DELETE.

Clustered vs non-clustered index?

Clustered: table rows are physically stored in index order (one per table, usually the PK). Non-clustered: separate structure pointing back to rows (many per table).

What is a covering index?

An index that contains all columns a query needs, so the query is answered from the index without reading the table.

What makes a query non-sargable?

Functions or arithmetic on the indexed column, leading-wildcard LIKE, implicit type conversion, or OR across columns — the index can't be used for a seek.

How do you find why a query is slow?

EXPLAIN / EXPLAIN ANALYZE: look for full scans, bad estimates, sorts and nested loops over big inputs; then index, rewrite, or reduce data.

Transactions & security
What is ACID?

Atomicity (all or nothing), Consistency (constraints hold), Isolation (concurrent transactions don't interfere, per isolation level), Durability (committed data survives crashes).

Name the isolation levels and the anomalies they prevent.

Read Uncommitted (none), Read Committed (dirty reads), Repeatable Read (+ non-repeatable reads), Serializable (+ phantoms and all others).

What is a deadlock?

Transactions waiting on each other's locks in a cycle; the database kills one. Avoid with consistent lock order and short transactions; retry on error.

What is SQL injection and how do you prevent it?

Untrusted input concatenated into SQL changes the query. Prevent with parameterized queries, allow-lists for identifiers and least-privilege accounts.

View vs materialized view?

A view is a stored query run on each access (always fresh, no storage). A materialized view stores the result (fast, but stale until refreshed).

Stored procedure vs function?

Procedures are called with CALL/EXEC, may modify data, return result sets/OUT params and control transactions; functions return a value/table and are used inside queries.

What is a trigger?

Code run automatically BEFORE/AFTER/INSTEAD OF an INSERT/UPDATE/DELETE — for audit logs, derived values and complex rules; use sparingly because it hides logic.
