# Security audit — 2026-11-07

Review of `learnvianotes/lvn-web` on `main` (`b7590c6`), the Next.js app: Firebase Google sign-in through the `/__/auth` proxy, the GraphQL client, R2-style pre-signed uploads, and the admin area.

This change fixes the High findings that are contained in this repo. Medium and Low items stay open, with the fix named, unless the change was a few lines and could not break a neighbouring feature. `app/(site)/layout.tsx` metadata, `sitemap`, and `robots` were not edited; another change is adding SEO metadata, a sitemap, robots, and the support email.

Checked by reading the auth proxy, session and redirect code, note and `/core` renderers, upload callers, admin pages, security headers, server routes, and `pnpm audit --prod`. No live Firebase project or production API was called.

## Fixed

### H1 — The browser PUT a file to whatever URL the API response named

**Severity:** High. **Where:** `features/notes/media.tsx` (`putToStorage`, previously around the `xhr.open('PUT', intent.uploadUrl)` call) and `features/beta/api.ts` (`putFile`). College ID, proof, imports, voice notes, and page pictures all use one of those two.

**Scenario:** The upload URL and headers come from the GraphQL response, not from a field the form lets someone type. A response that is not the real storage host — a cleartext API on a hostile network, or a bug that echoes a caller-supplied URL — makes the browser send the bytes there. That includes a college ID card. The previous code also set every header in the response except `Content-Length`, including a name containing a newline.

**Fix:** `lib/upload-target.ts` `storagePutRequest` (line 31). Development may use any `http:` or `https:` host, which is what the tests' `http://storage.test` needs. Sandbox and production require `https:` and an origin listed in `NEXT_PUBLIC_STORAGE_ORIGINS`. Userinfo in the URL and header names or values with a newline are refused. `Content-Length` is still left to the browser. Other headers the API asks for are still sent, because the contract says to send exactly those headers (`graphql/schema.graphql`, `UploadIntent`).

**Owner:** every sandbox and production build must set `NEXT_PUBLIC_STORAGE_ORIGINS` to the real storage origins (the deploy workflow already passes it). Without that list, uploads in those environments are refused rather than sent to an arbitrary host.

### H2 — A Meet link was rendered and sent without the Meet check

**Severity:** High. **Where:** `features/learning/Focus.tsx` (the session link and the buddy "Join" link). The allowed shape already existed as `meetUrlSchema` in `lib/contracts/validation/learning.ts` (line 93) and was not used on the way in or the way out. The GraphQL field is an unconstrained `String` (`graphql/schema.graphql`, `StartFocusSessionInput.meetUrl`).

**Scenario:** Someone starts a focus session with a link that is not a Meet code. Buddies who are studying see "Join" and the browser follows that address. A `javascript:` address would run in their page. An `https://` address on another host is a phishing page dressed as the study call. The input is `type="url"`, which does not run when the button submits through script.

**Fix:** `features/learning/meet.ts` `meetHref` (line 4). The form does not call `startFocusSession` unless the field is empty or matches `https://meet.google.com/abc-defg-hij`. Both links use that same check, so a value the API stored anyway is not turned into an `href`.

### H3 — Several `href`s used the raw string

**Severity:** High for addresses a person or a provider can influence; the same check is now used for the signed read URLs as well. React escapes attribute quotes, so the breakout is a scriptable scheme (`javascript:`, `data:`), not a quote inside the attribute.

| Sink | File |
| --- | --- |
| Project and provenance links on a public profile (cached, indexed for teachers) | `features/people/ProfileTabs.tsx` |
| Data-export download | `features/data/YourData.tsx` |
| Proof file open / preview | `features/verification/ProofPreview.tsx` |
| Moderation resource link (checked, then the original string was used as `href`) | `features/moderation/ModerationQueue.tsx` |
| Note image, video, and audio `src` / `srcset` | `features/notes/render/MediaBlock.tsx`, `srcSetOf` in `features/notes/media.tsx` |
| `/core` content links | `core-app/src/features/content/ContentView.tsx` |

**Scenario:** A profile `sourceUrl` or a moderation URL of `javascript:…` runs when the link is followed. `safeLinkHref` already rejected that scheme, but these call sites did not use it, or used it only as a boolean and then assigned the original string. A `srcset` value containing a comma could add a second candidate URL.

**Fix:** `lib/http-url.ts` `safeLinkHref` now returns the canonical `url.href` and rejects userinfo, so the string the browser stores matches the URL that was checked. Each sink above assigns that result. Rich-text links already went through `safeLinkHref` (`features/notes/render/RichText.tsx`).

### H4 — `/__/auth` would follow a redirect to any Google-owned suffix

**Severity:** High. **Where:** `lib/auth/firebase-auth-proxy.ts`, previously `REDIRECT_HOST`, which matched any host ending in `.google.com`, `.googleapis.com`, `.gstatic.com`, or `.googleusercontent.com`.

**Scenario:** The proxy fetches only this project's `firebaseapp.com` `/__/auth/…` path, then copies a 3xx `Location` onto the response. That response is same-origin (`https://<this site>/__/auth/…`). The old allowlist included `sites.google.com`, `storage.googleapis.com`, `www.google.com` (which has historically redirected onward through `/url?q=`), and any `*.googleusercontent.com` host. If the helper's `Location` can be influenced by the query string — the proxy forwards that query — the first-party origin becomes an open redirect onto attacker-controlled content hosted at Google, in the middle of the sign-in redirect chain.

**Fix:** `ALLOWED_REDIRECT_HOSTS` (line 39) is `accounts.google.com` and `apis.google.com`. A hop back to this project's `firebaseapp.com` `/__/auth/…` path is still rewritten onto this origin. `http:`, userinfo, and any other host become a 502 with no `Location`. The helper's own CSP is unchanged.

**Owner:** confirm a real Google sign-in still only redirects to those two hosts. If Google adds another hop, add that exact host. Do not widen the set back to every subdomain.

### H5 — SVG inner HTML, ink colour, and page pictures

**Severity:** High for the SVG sink when `/core` is on. Drawing colour and picture URLs are the same class of bug on notes, and were small enough to close with it.

**Where:**

- `core-app/src/features/content/ContentView.tsx` assigned `n.value` with `dangerouslySetInnerHTML` on `<svg>`.
- `core-app/server/fromHtml.ts` stores `el.innerHTML` of every `<svg>` (around line 168).
- `scripts/content/sanitize.mjs` removed `on*` attributes and a plain `href`, and did not treat `xlink:href` or `<foreignObject>` the same way.
- `features/notes/pages/PageEditor.tsx` used `stroke.color` and `image.href` from saved page JSON.

**Scenario:** A topic SVG containing `<a xlink:href="javascript:…">`, `<foreignObject>`, or an event handler survives the pipeline and runs in the page, because the renderer inserts the markup as HTML. A saved stroke colour of `url(https://…)` is a resource load from the drawing. A saved picture `href` of a scriptable scheme is assigned to `<img src>`. `/core` is off unless `NEXT_PUBLIC_CORE_ENABLED=true`, so the SVG sink is live only when those notes are served. The content in the repo today does not contain the payload; the renderer still accepted it.

**Fix:** `core-app/src/features/content/svg.ts` `sanitizeSvgMarkup` (line 25) runs before the assignment. It drops `script`, `foreignObject`, frames, event handlers, `javascript:` / `data:` / external `url()`, and keeps `url(#id)` so the existing diagrams still draw. The pipeline now removes `foreignObject`, `iframe`, `object`, and `embed`, and applies the link check to `xlink:href`. `inkColor` and `pageImageSrc` in `features/notes/pages/model.ts` allow only a hex colour and a `data:image/(png|jpeg|webp|gif)` URL, a `blob:` URL, or an `http(s)` URL.

### H6 — A production build did not require HTTPS

**Severity:** High. **Where:** `lib/launch-checks.ts` `launchProblems`, called from `next.config.ts` on `next build`. `lib/env.ts` accepts any URL. The access token is sent as `Authorization: Bearer` (`lib/apollo.ts`) and on the live socket (`features/notifications/live.ts`, `connectionParams`).

**Scenario:** `NEXT_PUBLIC_APP_ENV=production` with `NEXT_PUBLIC_API_URL=http://…` or `NEXT_PUBLIC_LIVE_URL=ws://…` still built. Anyone on the network path can read the bearer token. A local production build (Lighthouse, site URL `localhost`) is still skipped, as before.

**Fix:** `transportProblem` in `lib/launch-checks.ts`. A non-local production build fails when the site or API URL is not `https://`, or when a live URL is set and is not `wss://`. Empty values are left to env validation. Sandbox is not failed here; the image check in CI builds sandbox with HTTPS already.

### H7 — `pnpm audit --prod` reported one high advisory

**Severity:** High in the advisory, limited in this app. **Package:** `re2js` `>=2.2.0 <2.8.7` via `firebase` → `@firebase/firestore` → `re2js`. [GHSA-gg6h-894w-4m9c](https://github.com/advisories/GHSA-gg6h-894w-4m9c): quadratic time in a lookbehind. This app loads `firebase/app` and `firebase/auth` only (`lib/auth/google.ts`). Firestore is not called. The package is still a production dependency, and CI's `pnpm audit --prod --audit-level high` fails on it.

**Fix:** `package.json` `pnpm.overrides.re2js` is `>=2.8.7` (locked at 2.9.1). A repeat of `pnpm audit --prod --audit-level high` exits 0.

## Open

### M1 — Content-Security-Policy allows `'unsafe-inline'` scripts

**Severity:** Medium. **Where:** `lib/security-headers.ts` line 69 (`script-src` includes `'unsafe-inline'` and, in development, `'unsafe-eval'`). The helper policy in `lib/auth/firebase-auth-proxy.ts` lines 18–19 does the same. `style-src` is also `'unsafe-inline'` (line 70).

**Scenario:** Any HTML injection that reaches the page can run a script, because the policy does not distinguish the app's inline scripts from an injected one. The note renderer does not use HTML (see Passes). The remaining `dangerouslySetInnerHTML` scripts are the theme boot and the landing hint (`app/(site)/layout.tsx` line 57, the same script in `app/(core)/layout.tsx` and `app/global-not-found.tsx`) and JSON-LD, which escapes `<`.

**Why this was not changed:** pages are cached. Public notes revalidate hourly (`app/(site)/(public)/n/[slugId]/page.tsx`), profiles every five minutes, legal pages every minute. A per-request nonce baked into that HTML will not match the next response's `Content-Security-Policy`. The comment at the top of `lib/security-headers.ts` already says this.

**Proposed nonce CSP, for a decision:**

1. Add `middleware.ts` that sets `x-nonce` to a random value on each request and a `Content-Security-Policy` whose `script-src` is `'self' 'nonce-<value>' 'strict-dynamic' 'wasm-unsafe-eval'` plus the existing Google and analytics hosts. Drop `'unsafe-inline'` from `script-src` in production. Keep `'unsafe-eval'` only when `NODE_ENV` is development.
2. Pass the nonce into the root layouts and put it on the theme script, the landing script, and Next's own inline bootstrap. Next reads the nonce from the request when it is forwarded as the header it documents for this.
3. Stop caching the HTML of those layouts, or accept that cached HTML cannot carry a fresh nonce. That means `revalidate` on public notes, profiles, and legal pages becomes dynamic rendering, or a CDN caches the document without a CSP and the app sets CSP only on uncached responses. Hashes work for the two static boot scripts and do not work for Next's per-page bootstrap.
4. Leave the `/__/auth` policy as `'unsafe-inline'`. Firebase's helper document is not ours, and it is framed by the sign-in page. Do not put the site nonce policy on that response.
5. `style-src 'unsafe-inline'` can stay until styles move off attributes. It does not execute script under the script policy above.

This touches both root layouts. It was left out so it does not collide with the SEO metadata change in `app/(site)/layout.tsx`.

### M2 — Admin pages are guarded in the browser

**Severity:** Medium, as long as the API rejects the query. High if any admin field is missing an authorization check on the server, because this app will issue the query.

**Where:** `app/(site)/(app)/admin/layout.tsx` renders `AdminShell` and does not read a session. `features/admin/AdminNav.tsx` `AdminShell` (line 202) only chooses whether to show the sidebar. `components/auth/RequireSession.tsx` (line 11) redirects signed-out visitors in an effect, after the client knows the session. Several pages query immediately: `features/admin/AdminOverview.tsx` line 24 (`AdminMetrics`), and the same pattern in `AdminSettings.tsx`, `AdminPlans.tsx`, `AdminAccess.tsx`, and `features/admin/usage/panels.tsx`. `AdminUsers.tsx` waits for `canSeeSection` before it loads.

**Scenario:** A signed-in student opens `/admin/users` or `/admin`. The HTML and the admin operations are in the client bundle. The browser sends `adminMetrics` (and the other unskipped queries) with that person's access token. If the API returns the data, it is on the page. If the API returns `FORBIDDEN`, the page shows "not allowed" and the data does not. There is no second check in Next.

**Fix, not applied:** a Server Component or middleware that resolves the caller and returns 404 for everyone else, before the admin queries are sent. That needs a credential the Next server can see. See M3.

### M3 — Nothing for middleware to enforce, and the refresh cookie is not on document requests

**Severity:** Medium. There is no `middleware.ts`, so there is no matcher bug and no bypass of a gate that does not exist. The gap is the missing gate.

**Where:** `state/session.ts` lines 5–7: the access token stays in memory. `docs/architecture/web-addendum.md` lines 56–57: the refresh token is an HttpOnly cookie scoped to the API's `/graphql`. `lib/auth/session.ts` sends it with `credentials: 'include'` only to `NEXT_PUBLIC_API_URL`.

**Scenario:** A request for `/admin` does not carry a session the Next server can read. Middleware cannot see a cookie whose `Path` is `/graphql` when the path is `/admin`. Checking "any cookie is present" would still let every signed-in student through.

**Fix, needs a decision:** a site-scoped, HttpOnly session marker (not the refresh token itself) that middleware can require on `/admin`, plus a server round-trip that asks the API who the caller is. Until that exists, authorization is the API's job and the client checks are only the interface.

### M4 — A Google Apps Script URL is in the example env

**Severity:** Medium. **Where:** `.env.example` line 11, `NEXT_PUBLIC_FEEDBACK_URL`. It is a deployed web app URL (`/macros/s/…/exec`). The client bundle will contain it wherever that variable is set. No private key, service account, or `REVALIDATE_SECRET` is in the repo. Firebase web keys are public identifiers (`lib/env.ts`).

**Scenario:** Anyone who can read the repository can POST to that script. If the script appends to a sheet without its own check, the sheet is writable by the public. Rotating the deployment invalidates the committed URL.

**Fix:** confirm the script rejects anonymous writes, or move the URL out of the committed example and rotate the deployment. Not changed here, because emptying it disables `/core` feedback and the value may be intentional.

### M5 — The auth proxy reads the whole POST body

**Severity:** Medium. **Where:** `app/api/firebase-auth/[...path]/route.ts` line 19, `await request.arrayBuffer()`, then `lib/auth/firebase-auth-proxy.ts` forwards it to `https://<project>.firebaseapp.com/__/auth/<path>`. The project id comes from the environment, not the request. The path is one to four safe segments. Cookies are not forwarded, and `Set-Cookie` from upstream is not copied (covered by `tests/unit/auth/firebase-auth-proxy.test.ts`).

**Scenario:** A client can POST a very large body through this origin to that one Firebase host. That spends this server's bandwidth. It is not a general SSRF.

**Fix:** reject a `Content-Length` above a small limit (the helper's posts are short) before reading the body.

### M7 — `/core` still inserts highlight.js HTML and copies CSS through

**Severity:** Medium, and only when `/core` is enabled. **Where:** `core-app/src/features/content/CodeBlock.tsx` line 24, `dangerouslySetInnerHTML` of `highlight()` from highlight.js 11. `core-app/src/features/content/style.ts` `parseStyle` copies every CSS declaration into a React style object.

**Scenario:** highlight.js 11 escapes the code it highlights; a grammar bug that emitted raw HTML would run under M1. A `style` value in the content JSON can name `background-image` or `behavior`. The pipeline's `STYLE_ALLOW` list is not applied again at render. The content is the repo's, not a learner's note.

**Fix:** keep highlight.js current, and at render drop any style property outside the pipeline allowlist. Not done in this change so a content restyle is not accidental.

### M8 — Revalidate accepts a large JSON body

**Severity:** Medium for availability, not for cache poisoning. **Where:** `app/api/revalidate/route.ts` lines 13–20. The secret is compared with `timingSafeEqual` after a length check. Tags must match `note:<uuid>` or `public-notes`, at most 20.

**Scenario:** An unauthenticated client can make the server parse a large JSON body before the 401. The length check on the secret reveals the secret's length and not its bytes. A wrong secret does not revalidate.

**Fix:** cap `Content-Length` before `request.json()`, and compare a hash of the header to a hash of the secret so the lengths match even when the secrets do not.

### L2 — Development CSP allows any connect target

**Severity:** Low. **Where:** `lib/security-headers.ts` lines 48–65. When `NEXT_PUBLIC_STORAGE_ORIGINS` is unset, `connect-src` is `'self'` plus any `https:` (and `http:` / `ws:` when the site itself is `http:`). Production deploys set the storage list (`deploy.yml`).

**Scenario:** A development build's CSP does not stop a script from calling an arbitrary host. Production with the list set does.

## Passes

- **Markdown and notes.** `lib/markdown.ts` returns a tree. `features/notes/render/Markdown.tsx` and `CardView.tsx` render elements. Diagram cards are shown as text, not passed to Mermaid. Rich-text links use `safeLinkHref` (`RichText.tsx`).
- **Sign-in `next`.** `lib/auth/destination.ts` `safeNext` (line 28) rejects a scheme, a protocol-relative path, backslash, and control characters, then requires the parsed URL to stay on a fixed origin. `afterSignIn` uses it. The OAuth `next` is stored in `sessionStorage` and passed through `afterSignIn`.
- **Session.** Memory for the access token, HttpOnly refresh cookie, one refresh at a time in the tab and across tabs (`lib/auth/session.ts`). `lib/apollo.ts` retries once on `UNAUTHENTICATED`. Sentry drops cookies, the `Authorization` header, and query strings (`lib/observability.ts`), which matters because verify and reset links carry tokens in the query.
- **Clickjacking.** `frame-ancestors 'none'` and `X-Frame-Options: DENY` on `/:path*` (`lib/security-headers.ts` lines 83 and 91). `/__/auth` is `frame-ancestors 'self'` and `SAMEORIGIN` so the sign-in page can frame the helper, and that rule is listed after the site rule so it replaces it. `object-src 'none'`, `base-uri 'self'`, `nosniff`, referrer policy, and HSTS are set.
- **Proxy scope.** Upstream is `https://<projectId>.firebaseapp.com/__/auth/…` only. The project id is the env value, checked against a hostname shape. `..` and a newline in the query are rejected.
- **Secrets in the tree.** No PEM, service-account JSON, or private API secret. `REVALIDATE_SECRET` is read only in `lib/server-env.ts` (`server-only`).

## Decisions for the owner

1. **Nonce CSP (M1).** It means giving up ISR for the pages whose HTML would carry the nonce, and editing both root layouts. Say if that should be a follow-up.
2. **A cookie the Next server can see (M2, M3).** Admin authorization stays on the API until a site-scoped session marker exists. Say if the API should set one.
3. **`NEXT_PUBLIC_STORAGE_ORIGINS` (H1).** Sandbox and production uploads now fail closed when this is empty. Confirm the deploy value is the exact `https` origin of every pre-signed URL, including a custom download domain if one is used.
4. **Google redirect hosts (H4).** Sign-in must still complete with only `accounts.google.com` and `apis.google.com`. If a hop fails, name the host rather than restoring the suffix match.
5. **Apps Script URL (M4).** Rotate it, or confirm the script does not accept public writes.
6. **Moderate advisories (M6).** Leave them, or add overrides for `fast-uri`, `glob`, and `minimatch` in a dependency-only change.
7. **Sandbox HTTPS.** H6 binds production only. Sandbox image builds in CI already pass HTTPS URLs. Say if a sandbox build on `http://` should fail the same way.
